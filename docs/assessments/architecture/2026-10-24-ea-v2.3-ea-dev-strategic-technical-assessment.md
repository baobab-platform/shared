## 1. Executive conclusion

Baobab's architecture is increasingly coherent. The principal risk is no longer a lack of canonical concepts; it is the distance between accepted contracts and repeatable, safe, end-to-end enterprise capabilities. The next competitive advantage should come from making existing architecture simpler to adopt, test, explain and operate, rather than adding universally required platforms and gates.

**Recommended strategic shift:** from architecture-and-contract-output milestones to evidence-backed enterprise capability delivery. Measure successful journeys, consumer compatibility, tenant isolation, operational supportability and integration time; do not infer a production capability from an Accepted ADR, published schema, green source CI, disposable synthetic test or attractive UI.

The Accepted [ADR-SHARED-043](../../adr/ADR-SHARED-043-Development-Provisioning-and-Environment-Approval-Boundaries.md) corrects an important architectural process mistake: independent-human approval is not a prerequisite for ordinary isolated synthetic development. It does **not** relax same-Principal self-approval denials, native policy enforcement, separation in protected environments or legal/provider authorisation.

## 4. Verified drifts and risks to investigate

### 4.1 Consumer contract evolution versus semantic adoption (HIGH)

Selected current Shared consumer locks include CP cce79e12, IAM/Trade 1517429b, ERP e1da44e9, CMS 8f3f847d, Pulse f61de9c5 and Payments 2dc9a320, while Shared was at a2278294. Different pins are intentional and **not independently conformance failures**. Shared's contract-lock validation establishes valid source ancestry/existence/parsing and marks changed consumed files for review. It does not prove that an older consumer implements every newer semantic constraint.

**Recommendation:** contract-change impact analysis with a versioned consumer dependency graph, source references, producer/consumer compatibility, and mandatory selected negative/positive tests. Reject unsupported changes, not mere differences in commit age. Track changed versus unchanged consumed artifacts.

### 4.2 DEV-13 dependency graph may be read as a global release barrier (HIGH)

The DEV register lists DEV-04..12 as dependencies of DEV-13; EA-REL nevertheless explicitly supports progressive, capability-scoped release. If a generic graph scheduler interprets every dependency as unconditional, one unavailable optional engine could block an unrelated approved release.

**Recommendation:** distinguish programme prerequisites from capability-, provider-, Tenant-, Market-, legal-actor- and environment-specific release edges. Preserve separate protected approval and restore/rollback requirements. A real-money service must never inherit a CMS website's lower-risk admission.

### 4.3 Register currency (MEDIUM)

At observation, CP #434 was already merged but DEV-02's Shared row still described source baselines rather than that current merge. The register records a source observation as of 24 October; an observation within seven days can still become stale when dependencies change hours later.

**Recommendation:** add source-SHA-triggered REVALIDATION_REQUIRED to the *reporting projection*, without auto-promoting PASS or changing CP/owner authority. Keep historic records immutable and update the active register through reviewed source changes.

### 4.4 Root contract manifest coverage (MEDIUM; confirmation required)

Newer trade/v2 schema files (buyer-authority receipt, buyer commitment valuation and native classification) exist but were not enumerated in Shared's inspected root contracts.lock.yaml. It is **not proven** that this file is intended to be exhaustive.

**Recommendation:** determine the manifest's stated meaning; if it is publication inventory, validate completeness; if curated, provide a separately generated full schema index with owner, status and consumers.

### 4.5 Public/private documentation discrepancy (MEDIUM)

Shared README described repository visibility as Private, while GitHub repository metadata returned Public. This does **not** establish leaked secrets, but creates an inaccurate assumption for future contributor guidance.

**Recommendation:** correct the displayed metadata; separately review permitted evidence/redaction and repository visibility controls. Changing the README does not change repository access settings.

### 4.6 Repository hygiene (LOW)

Tracked scripts/__pycache__/...cpython-313.pyc entries were observed on Shared main and the .gitignore lacked Python cache exclusions. This is maintainability drift, not a runtime blocker. Remove generated bytecode in a narrow cleanup, prevent recurrence and verify no build depends on it.

## 5. Strategic risks and opportunities (proposals, not proven defects)

1. **CP authority availability and revocation:** specify which decisions may use bounded attestation, which native commitments require fresh authority, how expiry/revocation and partial outages behave, and how one-time receipt consumption is atomic. Default high-consequence uncertainty to denial; avoid a live CP round trip for every safe anonymous public content read.
2. **End-to-end native commitment coverage:** complete real buyer/seller -> governed Market/legal actor -> approved operation -> one-time native commitment -> durable recording/compensation tests. A contract fence on one code path must not imply all paths are protected.
3. **Correlated evidence rather than more authorities:** standardize read-only references joining request, decision, source/image digest, environment, scenario outcome, verifier, release scope, retention and sensitivity. Reuse CP/Shared owners; do not create a second CP or unauthorised evidence vault.
4. **Separate readiness dimensions:** display engineering, operational, governance and commercial readiness independently. Deployed does not imply enabled; enabled does not imply legal; source-green does not imply usable.
5. **Provider portability as demonstrated capability:** verify adapter conformance, data migration, rollback and resilience, not merely capability names and future provider registry entries.
6. **African-first operating conditions:** budget for low bandwidth, interrupted connectivity, jurisdiction/date/currency/language fidelity and clear uncertainty for estimated logistics/geospatial/regulatory data.
7. **Supply-chain and developer experience:** use exact images/versions, Software Bill of Materials, provenance, reproducible Codespaces and tested upgrade paths. Study OpenTelemetry for trace conventions, SLSA for artifact provenance, OWASP ASVS for web security and DORA metrics for engineering outcomes. These are external reference ideas, not automatic new Baobab authority.

## 6. Recommended platform/product strategy

**Product direction:** Baobab as an enterprise capability operating system for African markets, rather than a feature-count contest with monolithic ERP, commerce and logistics vendors.

- Composition should translate an authorised enterprise requirement into CP-governed eligible providers without asking business administrators to manage EngineInstances.
- Explainability should show deterministic reasons for DENY, BLOCKED, DEGRADED or READY, with provenance and a lawful next action.
- Reusable DEV-14/15 engine profiles should allow new headless providers to qualify IAM/CP/tenant isolation without making CMS or another unrelated engine a global dependency.
- Pulse should offer cited intelligence and assisted decisions, never self-promote statistical estimates into legal, financial, regulatory or security authority.
- Public websites for Nabhold, ZuriBeans and Thamani can pursue individually qualified CMS/content and truthful enquiry journeys before unavailable finance, native trading or transport provider capability. The announced 2 January 2027 public-site launch should not silently admit unsupported business actions.

**Avoid or defer** default Kubernetes/service mesh, Kafka-for-everything, new central authorization service, unqualified AI-driven compliance writes and speculative engine proliferation. Introduce each only against measured requirements, a clear owner and adoption/operations evidence.
