## 1. Executive verdict

**The Baobab Content Engine contains substantial implemented functionality that cannot be inferred from its single platform-provider declaration.** Payload 3 and Next.js implement multi-tenant collection security, canonical content identity, explicit content-scope inheritance, typed editorial models, Payload admin/REST/GraphQL, S3-compatible media metadata/storage, publication roles, events/outbox/retries, reconciliation, PostgreSQL 17 schema and fixtures, and reusable Nabhold/synthetic estate onboarding. Authenticated provider-route code enforces scoped bearer validation and current CP context before content resolution.

**Yet [`.baobab/capability-provider.yaml`](https://github.com/baobab-platform/baobab-cms/blob/a712797177924c875e50ed63a9c01ec34bd632c8/.baobab/capability-provider.yaml) declares exactly one canonical Shared capability — `content.entry.resolve@1` — with `implementation_status: PARTIAL` and `production_permitted: false`.** That conservative declaration reflects *integration support*, not the total number of internal editorial operations. Neither a native collection nor a tested internal function automatically becomes a Shared canonical provider key. Additional platform-resolvable capabilities require an explicit Shared catalogue/contract owner decision, not a proposed census here.

**Component readiness is relatively strong. Integrated platform readiness is not yet demonstrated.** At this main head, the following CI runs succeeded:
- [CMS CI #39669982069](https://github.com/baobab-platform/baobab-cms/actions/runs/39669982069): lint/typecheck, Vitest coverage, Next/Payload build, migrations against real PostgreSQL 17, two-process corporate-content verification, negative publication/tenant checks, separate synthetic fixture database, publish/withdraw/draft cycles and reconciliation. Informational npm audit succeeded as a workflow step, but uses `continue-on-error: true`, so it **does not certify absence of vulnerable dependencies**. PR-only dependency review is skipped on main pushes.
- [Foundation #39669983927](https://github.com/baobab-platform/baobab-cms/actions/runs/39669983927) and code-quality #39669981664 succeeded.

These are real component-synthetic tests, more valuable than source-only mocks. **They do not use an accepted live IAM-issued subject/validator token and current CP-issued active context with a running estate consumer**, do not satisfy seven INT-03C or fourteen NAB-03 cases, and do not confer staging or production approval.

**Current Shared EA-DEV has advanced beyond old CMS runbooks:** at the 24 October [official register](../../architecture/ea-dev-implementation-register.md), DEV-01, DEV-02 and **DEV-03** are `REAL_COMPONENT_SYNTHETIC_DATA / ACCEPTED` with bounded approved case receipts. DEV-04 (original seven INT-03C) and DEV-05 (all fourteen NAB-03) remain partial/source-runtime-unproven. CMS itself has not yet inherited a qualified DEV-05 outcome. Do not repeat old claims that no real CP/IAM exists, but do not infer a tested CMS downstream integration from DEV-03 passing.

## 5. High-consequence verification distinctions

### 5.1 Provider route is secure in design, but not a demonstrated connected service

The existing `POST /v1/content/resolve` first requires a bearer; then demands configured issuer, audience, JWKS, CP URL and validator-token source; verifies signed asymmetric workload JWT and `content:entry:resolve`, bound `context_id`, 8 KiB request limit, CP current same-subject context and local PRIMARY Organisation/tenant projection. It refuses wrong tenant, missing preview scope, ambiguous published records, absent types and unavailable CP. A separate development-only validator acquisition path in [#41](https://github.com/baobab-platform/baobab-cms/pull/41), [#47](https://github.com/baobab-platform/baobab-cms/pull/47) is bounded by specific disposable client, source deadline, introspection and fail-closed network controls.

**What it does not prove:** actual current IAM issuer/subject→CP→CMS caller/validator with an activated CP provider/instance/grant, and a real Nabhold/B2B estate consumer. Anonymous 401 and unconfigured 503 are genuine **negative** behavior, never a fabricated positive login.

### 5.2 Corporate collection model has advanced beyond original sparse CMS models

The five corporate content keys `home`, `navigation`, `footer`, `site-settings`, `group-profile` now have typed local source loaders, automatic tenant filtering and DTO projection. Three additional authored list collections (portfolio, sectors, insights) also exist; **the canonical provider route's [CONTENT_SOURCES](https://github.com/baobab-platform/baobab-cms/blob/a712797177924c875e50ed63a9c01ec34bd632c8/src/baobab/content-resolution/payload-source.ts) currently supports the five singleton keys only.** Direct Payload availability is not evidence of `content.entry.resolve` access for the three lists; they need an appropriate compatible consumer contract when adopted.

### 5.3 Distinguish the broader resolver library from the v1 public contract

The internal deterministic resolver supports specificity, override/inherit and separate compose functions, while Shared [content/v1](https://github.com/baobab-platform/shared/blob/main/contracts/content/v1/openapi.yaml) explicitly rejects COMPOSE with 422 in a single-record response. Locale fallbacks have no configured deployment chain. Unsupported semantics must stay explicit: **do not promise composed navigation or multilingual fallback simply because helper functions exist**. Define the required shape and backward-compatible Shared revision only if a real consumer needs it.

### 5.4 Actual CMS PostgreSQL 17 qualification is meaningful and scope-limited

The checked [CI migration gate](https://github.com/baobab-platform/baobab-cms/blob/a712797177924c875e50ed63a9c01ec34bd632c8/.github/workflows/ci.yml) runs a digest-pinned PostgreSQL 17 service, applies migrations with `push:false`, exercises real application hooks and tenant denials, tests separate-process persisted readback, then applies and cycles a second run-scoped synthetic estate. [Qualification runbook](https://github.com/baobab-platform/baobab-cms/blob/a712797177924c875e50ed63a9c01ec34bd632c8/docs/operations/pg17-component-qualification.md) and [INT-03 fixture runbook](https://github.com/baobab-platform/baobab-cms/blob/a712797177924c875e50ed63a9c01ec34bd632c8/docs/operations/int03-provider-fixtures.md) explicitly refuse normal/protected database use and label canonical references `UNRESOLVED`. Correctly count those tests as **component evidence**, not full DEV-05 acceptance.

### 5.5 Existing EA-DEV precedence governs integration

[EA-DEV register](../../architecture/ea-dev-implementation-register.md), **observed on 24 October**, already marks DEV-01, DEV-02 and DEV-03 `REAL_COMPONENT_SYNTHETIC_DATA / ACCEPTED`. CMS docs written on 9–21 October understandably contain older upstream rows. DEV-04 remains incomplete, and DEV-05 requires the **original fourteen NAB-03 case meanings** under actual IAM/CP/BFF/CMS. A new CMS roadmap is neither needed nor authorised.

### Security concern requiring a targeted test, not an unsupported claim

The active [Payload configuration](https://github.com/baobab-platform/baobab-cms/blob/a712797177924c875e50ed63a9c01ec34bd632c8/payload.config.ts) explicitly defaults `PAYLOAD_SECRET`, database credentials and MinIO credentials if env vars are missing, configures wildcard `CORS_ORIGIN` fallback, and with `PGSSLMODE=require` sets `ssl.rejectUnauthorized=false`. In a future protected deployment those settings **would be unacceptable unless separate enforced deployment/entrypoint controls reject them or override them**. This audit did not run a protected deployment and cannot conclude such controls are absent across Infrastructure; treating this as P1 triage with concrete startup/connection tests is justified. No secrets from a deployed environment were accessed.

### Product and strategic opportunities (not compulsory architectural scope)

- **One CMS engine for several independent corporate/digital estates.** Profile-driven, isolated content delivery can serve Nabhold and future subsidiaries/third-party clients without bespoke copies of Payload or granting parent Organisation access to a subsidiary Tenant.
- **Content publishing as a mature service.** The existing singleton and portfolio/sector/insight editorial models are immediately useful for marketing websites once connected identity, publication permissions, and actual estate content consumption are qualified.
- **Content provenance and event-driven coherence.** Canonical content IDs, separate mapping, outbox and cache revalidation provide a foundation for governance, multilingual delivery, search and Pulse-driven insight enrichment **without** building duplicate truth inside CMS.
- **Selective premium capabilities later.** Structured previews, advanced editorial approvals, rights-aware digital assets, language workflow, content accessibility/SEO and robust CDN/edge caching may justify further capability work when real estate demand and measurable outcomes exist. Do not create unsupported Shared canonical keys, a generic DAM or search provider as a condition for basic DEV-05.
