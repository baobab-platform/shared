## 1. Executive conclusion

**Baobab Trade is far more implemented than its canonical provider declaration suggests.** Source contains Medusa 2.21.2 native commerce, ZuriBeans B2B organisations and buyer onboarding, product assortment and UG/ZA catalogues, price/discount policies, inventory projections, payment and fulfilment orchestration, tax and trade logistics metadata, buyer principal/assurance/grants, governed spend ledgers, seller-binding and legal-actor authority, durable ERP/event bridges, Thamani retail simulation, Postgres-backed protected commit controls and extensive production-like synthetic tests.

**The provider declaration is nonetheless correctly conservative.** [`.baobab/capability-provider.yaml`](https://github.com/baobab-platform/baobab-trade/blob/29f0b9942044f1a2233a0144e561dc69cca28cd1/.baobab/capability-provider.yaml) lists three **planned** canonical Shared keys and **zero provider support entries**: `commerce.cart.manage`, `commercial.rfq.manage`, `commercial.quotation.manage`, each `CONTRACTED` and targeted to `baobab-trade.medusa`. Existing native Medusa carts do **not** implement Shared's exact quick-order B2B contract; no complete canonical RFQ/quotation routes were found in the checked route census. Do not equate 27 internal functional families below with 27 newly registered Shared provider capabilities.

**Trade-A achieved meaningful component/runtime qualification.** At [CI #39956056792](https://github.com/baobab-platform/baobab-trade/actions/runs/39956056792), all applicable jobs completed SUCCESS: formatting/lint/types/Vitest/build, pinned Shared contract conformance, real Medusa and PostgreSQL 17 native module/migration regressions, and a [Trade-A TA-08 integration harness](https://github.com/baobab-platform/baobab-trade/blob/29f0b9942044f1a2233a0144e561dc69cca28cd1/docs/plans/trade-a-ta08-real-runtime-acceptance.md) involving actual shipped image, live synthetic CP, signed test-issuer tokens and Postgres 17. [TA-08](https://github.com/baobab-platform/baobab-trade/blob/29f0b9942044f1a2233a0144e561dc69cca28cd1/docs/plans/trade-a-ta08-real-runtime-acceptance.md) records 18 bounded scenarios, a posture verifier and scoped certification of **`trade.order.commit` and `trade.draft-order.finalize`** for explicitly enabled nonproduction protected runtimes. `trade.order.create` remains denied for lack of a governed commit point; production remains denied. This is `REAL_COMPONENT_SYNTHETIC_DATA`, **not** actual IAM Hydra/Kratos production federation, ERP posting, PSP settlement, L4, staging GO or end-user acceptance.

**Latest important boundary:** [Trade #171](https://github.com/baobab-platform/baobab-trade/pull/171) added the universal native commitment fence of Proposed ADR-0036 in **SHADOW** mode. Its PostgreSQL trigger evaluates every TA-07 native cart commit/draft finalisation, writes append-only verdicts and can refuse missing/retired B2B/B2C classification, stale CP estate profile and missing B2B buyer receipt when independently activated. **It is intentionally not ENFORCED**. Under current code, buyer-authority and spend-reservation consumption in the same native transaction (CAA-06b) and connected provenance acceptance are still missing. The shadow gate is an engineering safeguard, not an activated commitment policy.

**Programme alignment:** [Shared current EA-DEV register](../../architecture/ea-dev-implementation-register.md) marks DEV-01/02/03 scoped development proofs `REAL_COMPONENT_SYNTHETIC_DATA / ACCEPTED` on 24 October; original seven DEV-04 INT-03C and fourteen DEV-05 NAB-03 cases remain open. DEV-07 ZuriBeans B2B and DEV-08 Thamani B2B logistics remain NOT_AUDITED/NOT_OBSERVED in the official register, regardless of this repository's native Trade tests. This audit cannot change that official progress without owning exact evidence.

Existing Thamani B2C test success does **not** prove that logistics business capability or justify relabelling historical B2C code as B2B. Owners should decide, scope and document coexistence/migration without deleting history. Seller/buyer B2B-v-B2C classification is per CP-governed estate/Market, never sales-channel name.

### Specific source-supported concerns — do not overinterpret

1. **`SHADOW` is a safety boundary, not a gap to bypass.** With no current live classification or composed B2B receipt, activating global ENFORCED would deny legitimate commitments, including the historically certified Thamani retail scenario if it lacked CP provenance. Decision 9 expressly requires staging/connected evidence and approved allocation/rollback before activation.
2. **TA-08 protected staging is not plug-and-play.** The owner's [TA-08 record](https://github.com/baobab-platform/baobab-trade/blob/29f0b9942044f1a2233a0144e561dc69cca28cd1/docs/plans/trade-a-ta08-real-runtime-acceptance.md) documents `NODE_ENV`/infrastructure mode tension, migration privileges, runtime/migration DB owner separation, connection headroom and role-/fence-posture. This report **does not** claim those operational defects have been reproduced after the audited commit; they are live revalidation items.
3. **Buyer authorisation is distinct from seller and payment authorisation.** A CP seller-binding ALLOW cannot substitute for buyer Principal, membership/role/Market/Site/amount spend or finance safety. Conversely, a buyer ALLOW cannot override merchant readiness, legal-actor restriction or native Postgres order fence.
4. **Business segmentation is governed.** Thamani B2B logistics is a separate Accepted DEV-08 business scope; the existing Thamani retail code demonstrates real B2C mechanics and can potentially coexist, but requires an owner decision on estate/market/legal permissions. Do not delete retail models or silently infer a logistics TMS.
5. **Historical docs must be contextualised.** [Trade README](https://github.com/baobab-platform/baobab-trade/blob/29f0b9942044f1a2233a0144e561dc69cca28cd1/README.md) and [engine boundaries](https://github.com/baobab-platform/baobab-trade/blob/29f0b9942044f1a2233a0144e561dc69cca28cd1/docs/architecture/engine-boundaries.md) include historical unimplemented market/mapping/outbox descriptions that coexist with later source. Audits must compare *current code/CI* and original evidence instead of re-stating old TODOs as active failures.

## 9. Platform opportunities

- **A credible multi-estate commerce platform without forks:** retain one Medusa-native engine and scope ZuriBeans B2B wholesale and Thamani's separate estate/market by CP-governed actual relationships. This is a re-engineering advantage only when cross-tenant, seller, currency, catalogue, legal-actor and native database fences are genuinely verified.
- **Governed B2B procurement:** existing membership/role/Market/Site/SoD and spend ledger provides a substantial foundation for professional procurement; expose canonical RFQ/quotation only after exact lifecycle/provider contract is implemented and consumed.
- **Native integrity as differentiation:** retain PostgreSQL-enforced consequential order decisions and bound append-only receipts, rather than trusting front-end toggles, Medusa UI roles or superficial gateway flags. Benchmark failure/rollback/recovery under actual runnable DB security posture.
- **Future engine extraction without premature microservices:** existing pricing, inventory, payments, fulfilment, compliance and ledger ports distinguish current native Medusa authority from possible future dedicated engines. Extract when consumer scale/authority justifies it, never by architectural fashion.
- **Africa-specific cross-border reach with accurate evidence:** UG/ZA multicurrency, landed cost, tax, tariff and Incoterms data structures are real reusable code; show simulated versus actual provider/legal determination, and measure market/product activation and audit traceability.
- **Readiness telemetry rather than inflated counts:** evidence-indexed native feature matrix, Shared provider declaration, current CP bindings and L4/DEV acceptance receipts can show stakeholders exactly what is safe today without another source of truth.
