## 1. Executive conclusion

**ERP is more implemented and better tested than the older foundation-stage summary and 7–8 October capability census would suggest.** At audited main, ERP uses iDempiere 13 (Orion LTS), PostgreSQL 17 and Java 17. It has real OSGi bundles, native posting/provenance migrations, a CP-aware JVM posting veto and true iDempiere/PG17 posting integration tests. The Python application service also provides bounded ERP v1 API routes, physical-inventory query adapters, CP-governed tenant/legal-actor mapping, idempotent Trade customer/order projection workers, own PostgreSQL outbox/inbox, provisioning, Finance baseline reference reads and documented release checks. **Do not describe the entire ERP as an unimplemented shell.**

**The capability declaration has two, and only two, canonical provider support entries:**

| Canonical key | Declared implementation status | Exact meaning and qualification |
| --- | --- | --- |
| `inventory.availability.query@1` | **IMPLEMENTED** | Canonical GET route, trusted tenant/context and SKU/warehouse mapping, query adapter and Shared conformance; **live physical-stock read against an actual iDempiere REST service is not established**. Candidate DRAFT registration can be prepared offline; CP activation/EA-09 not established. |
| `finance.order-consequence.process@1` | **PARTIAL** | Trade order event ingestion, crash-adopting execution, durable consequence projection, canonical query and event; shipment/invoice/posting-driven full order consequence progression and true native REST consumer end-to-end not demonstrated; no provider publication of PARTIAL support. |

The provider key `baobab-erp.idempiere` is `simulated:false`, `production_permitted:true` at the **declaration axis**. That field does **not** mean production is approved or iDempiere is provisioned for any customer. No OTHER internal feature listed here becomes an independent Shared capability key solely because it has a Python class, native iDempiere process or valid ERP ADR.

**The native posting breakthrough is real and important:** Main [CI run 39667531882](https://github.com/baobab-platform/baobab-erp/actions/runs/39667531882) succeeded in real iDempiere/postgres `idempiere-posting-integration` plus `erp-a-real-cp`, `native-finance-postgres`, Shared conformance, Python integration, JAR/image builds. The first Gate D CI driver uses a **synthetic CP over TLS** with genuine iDempiere financial journaling and DB assertions. ERP-A instead uses a **real CP binary**, signed test-issued workload tokens and iDempiere 13 + PG17 on both sides, for real-component synthetic purchase-side and ERP-B negative cases. Those prove their bounded local runtime/atomicity controls; **they are not original enterprise EA Gate D, L4, protected staging, real Finance approval, PSP settlement, production posting or genuinely accepted legal standing.**

**Primary unfinished execution gap:** native JVM posting and Python REST/order-to-cash/inventory/provisioning are **not** a single fully qualified end-to-end path today. The [REST p2 plugin documentation](https://github.com/baobab-platform/baobab-erp/blob/856c02343de499fa2ce287fe6238c2e097fd933e/idempiere/rest-api/README.md) says its vendor repository is empty by default; the tested `RestIdempiereClient` and Python order placement/stock/provisioning paths use fake engine transports. The native JVM finance fence should not be mistaken for proof that those application paths have exercised a running iDempiere REST provider. The report's verified distinctions matter for DEV-09/12.

**Architecture drift concern:** [`architecture/conformance.yaml`](https://github.com/baobab-platform/baobab-erp/blob/856c02343de499fa2ce287fe6238c2e097fd933e/architecture/conformance.yaml) is dated **8 October** and contains old “no live iDempiere”/“endpoints still 501” narrative subsequently corrected in parts, but never comprehensively reconciled with ERP #98–102 and #110. Its manual ledger does not include ADR-ERP-022/023 entries. It is unsafe as a *current* single readiness scoreboard without a dated crosscheck. Earlier [additional capability census](https://github.com/baobab-platform/baobab-erp/blob/856c02343de499fa2ce287fe6238c2e097fd933e/docs/architecture/capability-census-additional-areas-2026-10-08.md) self-contradicts its event-producer totals (narrative “two of eight” versus a table recognizing additional implemented producers); reconcile actual main producers rather than repeat either count.

## 6. High-consequence distinctions

### 6.1 Native PostgreSQL atomic posting — **qualified at a bounded level**

[ADR-ERP-022](https://github.com/baobab-platform/baobab-erp/blob/856c02343de499fa2ce287fe6238c2e097fd933e/docs/adr/ADR-ERP-022%20%E2%80%94%20Native%20Placement%2C%20Document%20Provenance%20and%20Posting-Authority%20Enforcement.md) and [current CI](https://github.com/baobab-platform/baobab-erp/actions/runs/39667531882) support a **real** posting proof: JVM hooks in shipped finance extension, transactionally checked `Fact_Acct` and document completion, proper iDempiere ID types, post/repost, rollback, duplicate/concurrency, direct SQL denial, purchase matching, class-exact provenance and kill-before-COMMIT recovery. The [ERP-A integration](https://github.com/baobab-platform/baobab-erp/tree/856c02343de499fa2ce287fe6238c2e097fd933e/idempiere/acceptance/erp-a) additionally verifies CP authority decisions from a real CP binary and signed test issuer. This **answers the old question whether CI could ever test atomic posting**: it now can and does for defined classes.

It does **not** mean every iDempiere class is allowed, that the application/REST order-to-cash code is that same posted path, that a native transaction spans CP or PSP, or that protected production has been approved. ERP-B vendor payment **recording** requires independent execution evidence; actual disbursement and settlement belong to Payments. Gate-D naming in the local owner job must not be confused with full EA/L4 Gate-D certification.

### 6.2 Exact provider/registration semantics

[`inventory.availability.query`](https://github.com/baobab-platform/baobab-erp/blob/856c02343de499fa2ce287fe6238c2e097fd933e/.baobab/capability-provider.yaml) `IMPLEMENTED` is source-contract evidence and its offline DRAFT generated support document is a construction artifact. [`finance.order-consequence.process`](https://github.com/baobab-platform/baobab-erp/blob/856c02343de499fa2ce287fe6238c2e097fd933e/.baobab/capability-provider.yaml) `PARTIAL` must not appear in ready registration. In both cases, CP alone owns runtime provider, EngineInstance, grant, CapabilityBinding and current health; actual consumer must prove tenant/mapping isolation and real engine evidence. There is no reason to expand canonical capability keys simply to mirror 26 source module families.

### 6.3 Real iDempiere posting and fake iDempiere REST transport can coexist

[Native harness](https://github.com/baobab-platform/baobab-erp/blob/856c02343de499fa2ce287fe6238c2e097fd933e/idempiere/acceptance/README.md) executes native actions inside the JVM and through SQL. [REST client](https://github.com/baobab-platform/baobab-erp/blob/856c02343de499fa2ce287fe6238c2e097fd933e/modules/integration/idempiere_client.py) is an independently implemented integration layer whose live p2 third-party plugin is not shipped by default. [Python order ingestion](https://github.com/baobab-platform/baobab-erp/blob/856c02343de499fa2ce287fe6238c2e097fd933e/modules/order_to_cash/inbox_execution.py) and [provisioning worker](https://github.com/baobab-platform/baobab-erp/blob/856c02343de499fa2ce287fe6238c2e097fd933e/modules/provisioning/execution.py) expressly disclose fake-engine acceptance. The native harness should be leveraged as a reusable test fixture for true REST POST/GET and existing canonical APIs, **not** used to certify untested routes.

### 6.4 ERP business and financial legal actor remain distinct from Tenant

A Shared CP `ErpAssignment` and accepted context name the canonical Tenant/Organisation/Market/mandates; ERP owns immutable native placement and approved Finance baseline. Neither ZuriBeans' trading brand nor Nabhold's holding-company relationship automatically grants `ACCOUNTING_ENTITY`, `INVOICE_ISSUER`, `CONTRACTING_PARTY` or `SELLER_OF_RECORD`. [Proposed 021](https://github.com/baobab-platform/baobab-erp/blob/856c02343de499fa2ce287fe6238c2e097fd933e/docs/adr/ADR-ERP-021%20%E2%80%94%20ZuriBeans%20Multi-Market%20AD_Client%20Topology.md) is not authority to establish two incorporation records or book Uganda activity through South Africa without a separately justified legal/finance determination. Keep iDempiere AD_Client/AD_Org as native records with provenance, not canonical identifiers.

### 6.5 What the event census actually says

[Event registry](https://github.com/baobab-platform/baobab-erp/blob/856c02343de499fa2ce287fe6238c2e097fd933e/modules/events/registry.py) lists **8 ERP-produced types and 2 consumed types**. The 8 October additional census initially states “two produced” but its own 10-line table marks `business-partner.changed`, `warehouse.changed`, `invoice.changed`, `payment.accounting-changed`, `order.consequence-changed` and `provisioning.changed` as produced; `inventory.availability-changed` and `customer.buyer-commercial-profile.changed` are marked absent. This is best described as **six recognized source producers in the dated census, two explicit gaps**—**not** current run-qualified 6/8 producer certification. The next owner census should reverify actual outbox calls, event IDs/schema and current consumer receipt for every one at `856c02343de499fa2ce287fe6238c2e097fd933e`, and record exact exceptions.

### 6.6 Baobab People and the newer execution baseline

[ADR-ERP-023](https://github.com/baobab-platform/baobab-erp/blob/856c02343de499fa2ce287fe6238c2e097fd933e/docs/adr/ADR-ERP-023%20%E2%80%94%20Baobab%20People%20African%20Workforce%2C%20Payroll%2C%20CDSoftware%20Re-engineering%20and%20PostgreSQL%2017.md) establishes a forward-looking competitive African enterprise workforce/payroll direction and PG17 adoption.
